# From a service request to an enquiry

The current priority is a visitor following a recommendation or a reply to a
specific request. The page should answer what can be built, how it relates to
their current tools, how work starts and how scope, price and handover are agreed.
This is a project recommendation, not a claim about channel conversion rates.

## Match the link to the task

Use the service page that answers the actual request. Use the homepage when the
scope is unclear. Links below are production destinations; local changes appear
there only after a production deployment.

In a reply, refer to the person's stated task, say which part Atomic Concept can
handle and ask one useful scoping question. For an integration, ask which programs
and which data need to be connected. For automation, ask what triggers the process
and what should happen next. Avoid a generic list of every technology or service.
These are drafting guidelines; no public posts or private messages are sent.

## Implemented on the site

- A short service explanation and an enquiry link before each software article.
- A distinct opening scene, with contextual smaller images inside the article.
- Visible homepage answers about the first message, existing tools and scoping.
- Contact guidance that accepts a business problem without a technical specification.
- Service-specific 1200 x 630 share images and localized metadata in static HTML.

[Open Graph](https://ogp.me/) defines the title, description, URL and image
metadata used to describe a shared page. The local export checks the metadata and
image files. Actual rendering and cache updates on Facebook or another service
need verification after publication; local availability is not that evidence.

## Next priorities

1. **Public evidence of work.** Select two or three publishable examples with the
   required owner/client permission. Explain the original task, constraints, the
   implemented scope and a verifiable result. An anonymized example is useful
   when it stays specific. Label hypothetical demonstrations as examples; do not
   present generated screenshots as client work.
2. **A useful first response.** Keep a brief enquiry record: requested task,
   current tools, desired result, timeframe, budget if known and next agreed step.
   Prepare an estimate around a bounded scope and acceptance criteria. Do not
   invent a fixed package price before delivery costs and scope are understood.
3. **Lightweight measurement.** Add service-to-contact navigation and confirmed
   submission results to the existing analytics setup. Use campaign parameters
   for links placed deliberately, without collecting form text or email addresses
   in analytics. Compare qualified enquiries and actual projects, not visits alone.
4. **Choose specialisation from enquiries.** Review which tasks recur and which
   projects are a good fit. Then add a specific use-case page backed by evidence.
   Avoid many near-identical industry pages or a blog written only for keywords.

Keep the current plain company voice. Do not add founder biographies, GitHub
profiles, invented testimonials, customer counts, savings or delivery guarantees.
